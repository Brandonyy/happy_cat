# 第三关性能定位记录

日期：2026-11-14。用户反馈：微信真机在球堆满后持续卡顿。

## 当前判断

优先核查微信真机的 2D 物理求解开销。本地对照显示，活跃球数量和多边形碰撞体会显著增加物理耗时；这些结果尚未确认手机上的实际瓶颈，不能换算成真机帧率或优化收益。

本轮没有修改游戏脚本、关卡、碰撞体配置或引擎选择。所有开关、数量及碰撞体变体只在独立测试预览内生效。

## 当前第三关配置

- 总球数 90，同时生成上限 42，候补 48；球缩放 0.94。
- 已启用圆/矩形简化碰撞体、固定旋转及阻尼。
- 物理求解迭代次数为速度 4、位置 2；固定步长约 1/60 秒，最大子步数 1。
- 所有场上球允许休眠；实测静止足够久后能够休眠，未发现永久不休眠的证据。
- 当前预览使用 JavaScript Box2D：`b2PhysicsWorld` / `b2World`。本地现有微信构建也包含 42 球限制、简化碰撞体及 4/2 迭代次数，但没有核对手机正在运行的包是否与本地构建一致。

## 测量环境与方法

Windows 桌面浏览器 Chrome 157，Intel UHD Graphics 630，画布 996×883，设备像素比 1。共 15 段采样、5,988 帧；正式测量没有隐藏页面帧，也没有捕获运行异常。

使用真实场景、物理系统、碰撞体和渲染；计时覆盖物理系统、Box2D 求解、组件逻辑、引擎渲染提交和帧间隔。引擎性能面板在各组测量中保持开启。

每个数量/形状变体重新进入第三关。数量、迭代次数及刚体的固定旋转和阻尼按测试配置控制。随机种子用于降低差异，但场景装载、帧时序和实际接触数量仍存在波动；各条件只有一轮样本，用于定位开销，不作为精确收益承诺。
