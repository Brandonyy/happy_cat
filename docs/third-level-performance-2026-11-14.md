# 第三关性能定位记录

日期：2026-11-14。用户反馈：微信真机在球堆满后持续卡顿。

## 当前判断

优先核查微信真机的 2D 物理求解开销。本地对照显示，活跃球数量和多边形碰撞体会显著增加物理耗时；这些结果尚未确认手机上的实际瓶颈，不能换算成真机帧率或优化收益。

本轮没有修改游戏脚本、关卡、碰撞体配置或引擎选择。所有开关、数量及碰撞体变体只在独立测试预览内生效。

## 当前第三关配置

- 总球数 90，同时生成上限 42，候补 48；球缩放 0.94。
- 已启用圆/矩形简化碰撞体、固定旋转及阻尼。
- 物理求解迭代次数为速度 4、位置 2；固定步长约 1/60 秒，最大子步数 1。
- 所有场上球允许休眠；实测静止足够久后能够休眠，未发现永久不休眠的证据。
- 当前预览使用 JavaScript Box2D：`b2PhysicsWorld` / `b2World`。本地现有微信构建也包含 42 球限制、简化碰撞体及 4/2 迭代次数，但没有核对手机正在运行的包是否与本地构建一致。

## 测量环境与方法

Windows 桌面浏览器 Chrome 157，Intel UHD Graphics 630，画布 996×883，设备像素比 1。共 15 段采样、5,988 帧；正式测量没有隐藏页面帧，也没有捕获运行异常。

使用真实场景、物理系统、碰撞体和渲染；计时覆盖物理系统、Box2D 求解、组件逻辑、引擎渲染提交和帧间隔。引擎性能面板在各组测量中保持开启。

每个数量/形状变体重新进入第三关。数量、迭代次数及刚体的固定旋转和阻尼按测试配置控制。随机种子用于降低差异，但场景装载、帧时序和实际接触数量仍存在波动；各条件只有一轮样本，用于定位开销，不作为精确收益承诺。

## 堆叠阶段对照

下表是对应堆叠阶段内的每帧平均耗时。66 球和多边形组均为临时压力测试条件，不代表当前正式配置。

| 条件 | 物理耗时 | Box2D 求解 | 渲染提交耗时 | 平均 FPS | 接触数量均值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 当前 42 球、简化碰撞体 | 1.205 ms | 1.135 ms | 0.473 ms | 60.0 | 95 |
| 42 球、原多边形碰撞体 | 2.588 ms | 2.525 ms | 0.368 ms | 59.9 | 157 |
| 66 球、简化碰撞体 | 2.508 ms | 2.431 ms | 0.397 ms | 59.9 | 208 |
| 66 球、原多边形碰撞体 | 10.573 ms | 10.484 ms | 0.461 ms | 57.9 | 485 |

66 球、多边形组的物理耗时 P95 为 20.1 ms，已经超过 60 FPS 下每帧约 16.7 ms 的时间预算。CPU 的绝大部分开销发生在 Box2D 求解内。

当前配置在出球完成后的 7–15 秒内，平均有 42 个球保持活跃。15–22 秒内活跃数开始下降，后续观察到全部休眠。应分别看待活跃堆叠和休眠后的性能。

## 相同时段的开关复核

各组重新进入第三关，等待约 7 秒后采样 6 秒；各组场上都是 42 个球。

| 条件 | CPU 帧耗时均值 | 物理耗时均值 | 渲染提交均值 | 活跃球均值 |
| --- | ---: | ---: | ---: | ---: |
| 正常 | 2.058 ms | 1.333 ms | 0.623 ms | 42 |
| 只关闭球 Sprite | 2.634 ms | 1.806 ms | 0.734 ms | 42 |
| 只关闭物理 | 0.813 ms | 0.001 ms | 0.707 ms | 42 |

关闭物理时 CPU 开销明显下降。关闭球绘制没有观察到稳定下降，但该组实际接触数量也更高（约 106，正常组约 92），存在场景时序和采样噪声，不能把两组差额解释为绘制的精确成本。

此前在同一场景依次关闭物理和绘制的观察受自然休眠影响，因此以上重新入场的对照用于复核。桌面 Renderer 计数主要反映 CPU 渲染提交耗时，不等同于 GPU 实际耗时，也不能排除手机 GPU 或驱动瓶颈。

## 出球与内存

- 当前配置的出球阶段平均 FPS 59.2，帧间隔 P95 为 19.0 ms，最大 56.5 ms；存在少量启动尖峰。
- 单个球创建平均 1.107 ms，P95 为 1.6 ms，最大 2.8 ms。
- 出球阶段渲染提交最大 39.4 ms，说明开局短暂卡顿还需单独检查资源上传或初始化；这与用户反馈的堆满后持续卡顿是不同的观察窗口。
- 稳定阶段纹理占用约 112.68 MiB，需关注手机内存预算；本轮未观察到第三关持续增加纹理占用。JS 堆数值受到垃圾回收影响，没有据此判断内存泄漏。
